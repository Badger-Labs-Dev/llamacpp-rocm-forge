# Work package 07 — integration and real-GPU verification gate

## Objective

Prove the refactor’s stated boundaries before scheduling another full deep-context campaign:

- static planning prunes only known-impossible GPU KV allocations;
- uncertain cases still reach runtime probing;
- fixed 2048/2048 configuration is used everywhere;
- runtime allocation errors and timeouts are not relabeled as static facts;
- artifacts accurately describe coverage and status.

## Prerequisites

All applicable packages 01–06 merged into one integration branch. Do not run this gate on a worktree containing accidental changes to historical `results/` artifacts.

## Automated verification

Run from repository root using the project’s established test command. At minimum:

1. Focused domain tests for feasibility and planner.
2. Focused auto-tune/campaign characterization tests.
3. Artifact/manifest/status tests.
4. Entire benchmark test suite.

Record exact commands and outputs in the PR/session handoff.

The full suite must be green before GPU work. A mock-only suite is necessary but insufficient.

## Static-planning integration fixture

Build an in-memory/small fixture with all three outcomes:

| dtype/depth | Expected planning outcome |
|---|---|
| q4_0, deep | eligible or unknown/runnable |
| f16, deep | statically excluded only if exact supported calculation proves it |
| unsupported architecture/depth | unknown/runnable |

Assert:

- excluded pairs cause zero Docker invocations;
- unknown pairs still cause a runtime probe;
- request ordering and original context limit are preserved;
- static accounting is represented verbatim in the manifest.

## Supervised real-GPU smoke test

Use a small representative GGUF before the Qwen3.8 target model. Do not launch a full campaign yet.

### Smoke test A: default GPU KV semantics

Run with fixed 2048/2048, `-ngl 0`, default or explicit `-nkvo 0`.

Verify from logs:

- GPU backend loaded;
- KV buffer placement/size visible;
- actual configuration has `no_kv_offload=false`;
- result classification is `ok` if successful.

### Smoke test B: contrast-only host KV control

Run equivalent configuration with explicit `-nkvo 1`.

Verify changed placement behavior. This proves assumptions; it must not become the normal campaign configuration without separate design approval.

### Smoke test C: dtype coverage

At a representative depth, execute q4_0, q8_0, and f16 with fixed 2048/2048.

Verify:

- command/config tags contain the correct dtype;
- q4 → q8 → f16 execution order in the orchestration path;
- no batch/ubatch grid or fallback invocation occurs;
- quantized KV retains valid flash-attention behavior.

### Smoke test D: runtime-failure classification

Select a bounded, supervised context/model condition likely to fail or time out without destabilizing the host. If a safe deliberate failure cannot be produced, use an integration test plus a known historical log fixture.

Verify the outcome remains one of:

```text
allocation_failed | timed_out | configuration_error | process_error
```

and does not add a static exclusion or make a lower planned depth disappear.

## Qwen3.8 targeted check

Only after the smoke tests pass and Qwen3.5 exact support is enabled by package 01/02:

1. Generate the per-dtype plan using actual GGUF metadata and R9700 reportable VRAM.
2. Review the generated byte accounting manually before launch.
3. Confirm the intended f16 candidate behavior—63,488 retained and 96,256+ excluded—comes from the finalized exact formula and validated reserve, not the legacy estimator.
4. Run a single controlled deep feasibility probe, not a full campaign.
5. Inspect logs/artifacts before approving a full rerun.

If Qwen3.5 remains `unknown`, confirm that it is not statically pruned and make the runtime cost explicit in the launch decision.

## Final acceptance checklist

- [ ] No normal campaign runs batch/ubatch grid probes.
- [ ] Every normal config uses `batch=2048`, `ubatch=2048`.
- [ ] Static exclusions have exact bytes, reason, and scope.
- [ ] Unknown cases are never skipped statically.
- [ ] q4/q8/f16 have independent depth eligibility.
- [ ] Runtime timeout differs from allocation failure and differs from static exclusion.
- [ ] A completed eligible envelope yields `finished` despite higher static exclusions.
- [ ] Summary/manifest/metadata/status marker agree.
- [ ] Unit suite and real-GPU smoke evidence are retained.
- [ ] No pre-existing deleted/untracked result files were staged, restored, or deleted.

## Completion report format

The verifier’s handoff must include:

1. commit SHA and clean/dirty status summary;
2. test commands and outcomes;
3. GPU/image/model identifiers;
4. smoke commands and relevant log excerpts;
5. plan outcome counts by dtype (`eligible`, `excluded`, `unknown`);
6. selected final config or a clear statement that a full campaign remains blocked;
7. any assumption that limits portability to a different GPU/build/configuration.
